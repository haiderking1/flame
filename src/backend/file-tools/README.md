# File tools

`ls`, `read`, `edit`, and `write` run in the backend through the same sequential agent loop as Bash. They resolve relative paths against the session's folder (its worktree, or the project checkout); absolute paths and `~/` are supported. There is no approval policy or filesystem sandbox. Files have the same user-level access exposure as Bash; these tools are not a credential boundary.

## Contract

- `ls` lists one directory without recursion. `path` defaults to the session's folder (`null`, omitted, or empty); `limit` defaults to 500 and accepts a positive safe integer. Entries are sorted alphabetically, case-insensitively, include dotfiles, and show `/` after directories (including symlinked directories). Listing content is limited to 50 KiB without cutting names; truncation and unavailable entries are reported in the summary. Names containing control characters, quotes, or backslashes are JSON-escaped to keep entries unambiguous and on one line. Missing/inaccessible directories and file targets return errors, not empty listings. Increasing the entry limit does not remove the byte bound. No shell process is started, and directory/symlink contents are never recursively traversed.
- Text-content operations accept regular UTF-8 text, at most 16 MiB. Read also supports PNG, JPEG, WebP, and GIF images as described below. Unsupported binary, invalid UTF-8, and NUL-containing text files are rejected rather than decoded lossily. Devices, FIFOs, sockets, and directories are not read. Reads open nonblocking and verify descriptor/path identity before returning.
- `read` uses 1-based `offset` and returns at most 2000 complete lines / 64 KiB. `next_offset` is the explicit continuation cursor; `null` means EOF. Individual oversized lines get an explicit error. Empty files have zero lines. Output omits the BOM and normalizes CRLF to LF; `sha256` always hashes original bytes, including BOM and line endings. No unbounded split/line array is allocated.
- `edit` matches every nonempty `oldText` exactly once in the same original file. Even overlapping occurrences count as ambiguous. Multiple ranges must be disjoint; validation of every replacement precedes writing. There is no fuzzy matching. Uniform CRLF and UTF-8 BOM are preserved. Mixed endings or lone CR are rejected explicitly rather than normalizing unrelated text.
- `write` writes content exactly as provided. `expected_sha256: null` means create only. Replacing an existing file requires its current raw-byte SHA-256, obtained from `read`. Edit accepts the same hash guard, with null permitting exact matching against a fresh snapshot. Stale hashes fail without replacing the file.
- Encoded file-tool arguments are limited to 1 MiB. There are at most 100 replacements per edit and 1024 durable file-operation records per session. Existing 32-step and 16-calls-per-response limits still apply. Provider input retains separate 8 MiB text/tool and 64 MiB image budgets; durable turn output retains its 256 MiB limit.

## Image reads

Read identifies supported image bytes even without an image extension; a recognized image filename with damaged/unsupported bytes fails explicitly. It captures one bounded, identity-checked regular-file snapshot (symlinks resolve normally), then uses the shared backend normalization pipeline: at most 20 MiB, 40 megapixels, fit within 2000×2000 without upscaling, EXIF orientation, and less than 4.5 MiB of base64. Animations become a disclosed still frame. Offset/limit do not crop or paginate an image. Known text-only models get an explicit tool failure, not a silently omitted visual result. Edit/write remain text-only.

Session version 9 adds `file_operations.image_id`, a unique foreign-key reference to a privately stored original/prepared image. The source is never modified. Image metadata, ownership and the operation result commit together; claim/result recovery never rereads a changed or deleted source under the same call ID. Draft cleanup cannot delete Read snapshots, and they do not occupy draft upload slots or become user-message attachments. Session deletion owns their lifecycle. File publication before a failed SQLite commit or crash may leave private orphan files, as with attachment publication; no operation is automatically replayed to repair them.

Persisted tool output contains metadata only. At inference time the backend reconstructs `function_call_output.output` as a real Responses array of `input_text`/`input_image` blocks with `detail: auto`, not base64 inside ordinary JSON text. Completed/interrupted history and model/account switches retain visual context; compaction can see image pixels and uses visual-token estimates rather than counting base64 as text. A summarized prefix may drop pixels from active context, but the saved Read preview/original remains available in history. Uploads and Read share two normalization-worker slots with bounded, cancelable waiting. Stop/shutdown abort owned preparation without changing the source file.

## Mutation lifecycle

1. Validate arguments and resolve paths relative to the session's folder.
2. Commit a session-owned SQLite operation claim before creating directories or touching files. Claims include turn/call identity and an argument fingerprint, not duplicated full file contents.
3. Resolve existing symlinks to their target and acquire the process-wide canonical-path mutation queue. Read a bounded, identity-checked snapshot, then validate the expected hash and every edit.
4. Write an exclusive, same-directory temporary file, preserve the existing POSIX owner/group and ordinary mode bits, and fsync its content. Existing files must be writable, owned by the current user, singly linked, and have no special permission bits.
5. Recheck path resolution, inode metadata, and content hash immediately before commit. Rename over an existing file, or hard-link a new file into place with atomic create-if-absent semantics. Fsync the directory and any newly created parent-directory entries. Temporary-file cleanup is attempted on every path.
6. Save the result to the operation ledger, then checkpoint it into the turn before the next provider request. A result-save failure stops the loop; it never becomes a suggestion to rerun the operation.

There is no await-abort race that releases the file queue while a filesystem write is still in flight. Stop is checked between I/O operations and before commit. Once a rename/link succeeds, cancellation does not claim the change was rolled back. Directory sync/cleanup failure after commit is reported as **uncertain**, explicitly stating that replacement occurred. Failed creation can leave newly created parent directories. A crash or cleanup failure may leave a `.flame-*.tmp` sibling; it is never used to replay a write.

Existing symlinks remain symlinks. Dangling links are not silently replaced. Multiple hardlinks are rejected because atomic replacement would break shared-file semantics. Atomic replacement changes the inode; ACLs, extended attributes, sparse-file layout, and other specialized filesystem metadata are not copied. Use deliberate Bash operations for metadata-sensitive files. Windows is not a supported atomic-mutation platform in the current Linux-first backend.

The queue serializes Flame's own file-tool mutations, including aliases across sessions. It cannot lock out editors, Bash, other backend processes, or adversarial filesystem changes. Precommit checks catch observed external changes, but portable path-based rename is **not** an atomic compare-and-swap against external writers. There remains a narrow check-to-rename race. Stop cannot interrupt a kernel-blocked filesystem call, and power-loss durability ultimately depends on the filesystem honoring fsync.

## Recovery and presentation

Session database version 5 adds the operation ledger; version 6 transactionally extends it for `ls`, preserving existing records, row ordering, and turn IDs. Versions 1–5 migrate through the existing stages. Reusing the same turn/call returns its saved outcome; an unfinished claim returns uncertainty instead of executing. Different arguments under the same identity fail. A short mutation ledger informs later turns about interrupted effects without injecting complete file contents. `ls` and `read` results are excluded from that additional mutation context. Listings still use durable call claims and saved outcomes: repeated call IDs return the recorded snapshot instead of silently refreshing it. Read-only cancellation/storage failures do not claim that files might have been modified.

Both live snapshots and saved history restore durable tool results that were recorded just before a turn checkpoint failed. Public work projections contain the operation label/path, status, summary/error, a bounded read/listing preview, and optional image metadata/checksums for verified downloads. Text hashes, provider arguments, reasoning, image base64, and private envelopes are not exposed through this projection. Image results use the existing authenticated chunk-download path and zoomable viewer inside the tool's single disclosure. File rows are expandable alongside Bash rows and retain their results after reload. They do not invent process output or offer a process Stop button; composer Stop cancels their parent turn.

Regression sources live in `tests/file-tools.test.mjs`, `tests/ls.test.mjs`, `tests/ls-migration.test.mjs`, `tests/file-tools-agent.test.mjs`, and `tests/read-images*.test.mjs` (plus the image UI fixture), including the actual Responses parser → tools → provider follow-up → session history path. They must be built before running. Test execution was intentionally deferred during implementation at the user's request.
